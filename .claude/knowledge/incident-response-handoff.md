## 確定した制作方針

- 冒頭に Why、What、How を置き、その後に各論を示す。
- 承認後に「対応フローの決定」と「教育と実装」を並行して始め、両方が整い次第制度を導入する。固定の導入期間は置かない。
- 対応プロセスは7工程。検知と社内報告、一次評価とレベル判定、事実確認と証拠保全、経営判断と専門家確認、対外発信と顧客対応、収束判断と振り返り、規程と教育への反映。
- 主管部署は事象の種類で決める。サービスと製品は事業責任者と技術責任者、情報とプライバシーは情報管理または情報システムの責任者、組織と人は人事または経営の責任者、契約と当局と権利は小川さんと関係部門、報道と風評と対外説明は広報責任者。
- レベル判定は影響範囲、深刻度、継続性、対外性の4軸。最も高い評価を暫定レベルとし、Level 3 以上は経営へ上申する。
- 確定ノートにある目標時間案は3つ。発見後10分以内の報告、社内報告の受付から30分以内の暫定レベル判定、上申後30分以内の Level 3 以上の最終決定。
  - 資料にはこれ以外の時間（60分、120分、4時間、5営業日、30日）も置かれているが、確定ノートに根拠の記録がない。
- 第一報テンプレートはプロダクト内、サービスサイト、PR TIMES、CS個別の4種を Appendix に置く。
  - 発信前に確認済み事実、影響範囲、現在の対応、次回更新予定を整理し、推測、原因の断定、未確認の復旧時刻、責任主体の断定を避ける。
- 45分の基礎研修は5部構成。0〜10分 当社のリスク、10〜18分 なぜ対応が重要か、18〜25分 インシデント発生、25〜38分 発生時の対応フロー、38〜45分 窓口確認と報告演習。
- 研修で覚えてもらう発生時の行動は7段階。異変を発見、安全確保と操作停止、画面や URL の保存、報告窓口へ連絡、主管部署が一次評価、指示に従い対応、変化を追加報告。
- 研修の事例は実在事故として書かず、研修用の仮想事例と明示する。
- 「発見者がしないこと」は報告内容とは別スライドに置く。

## Google Slides 編集時の落とし穴

- 文字の置換は、先に新しい文字列を index 0 に insertText し、その後ろの旧文字列を deleteText で消す。
  - 旧文字列を先に全削除すると、残った改行の書式（Arial 14pt）を新しい文字が引き継ぎ、書体がずれる。
  - HOW と承認依頼のスライドの書体ずれは、この経路で起きたと考えられる。
- deleteText の範囲は新しい文字列の文字数から数える。文字数の数え間違いで末尾の1文字が残る事故が1回起きたので、送信前に Python の len で数える。
- 置換後は updateTextStyle を range ALL で当て、書体、サイズ、太さ、色を周囲と揃える。
- 全36枚の masked read は約50万文字になり、ツール結果はファイルに保存される。
  - 整形スクリプトで、オブジェクト ID、座標、書式、文字列の一覧に落としてから読む。
- サムネイルの URL は curl で取得できる（許可ドメイン lh7-us.googleusercontent.com）。修正後の確認はこれで足りる。
- 罫線（line 要素）の transform は scaleY を 0 にする。1 にすると線が斜めになる。
- duplicateObject で付ける objectId は5文字以上にする。4文字以下は拒否される。
- 高根さんが編集中は requiredRevisionId が頻繁に不一致になる。文字列の範囲を直前に検算したうえで、ガード無しで送るほうが速い。
