# ひとり広報の見直しを、5体のエージェントに任せた話

PR担当として、毎月いくつかの原稿を書いています。インタビュー、プレスリリース、note。書くこと自体は嫌いではありません。困っていたのは、書いたあとの見直しでした。

ひとり広報の現場では、自分の原稿を見るのも自分です。書いた直後の頭は自分の文章を疑えません。だから一晩寝かせて翌日に読み直したり、声に出して音読したり、回り道で粗を見つけてきました。効果はあるものの、時間がかかります。公開までのリードタイムが見直しの工程でいつも伸びていました。

そこで見直しを含めた原稿づくりの流れを Claude Code のカスタムエージェントに移しました。1体の万能AIに丸投げするのではなく、役割を分けた5体のサブエージェントで編集部をつくっています。今回は、その中でも私が時間を取られていたライティングとレビュー、それと学習の回し方を共有します。

## 受付エージェントと、4つの担当エージェント

編集部は5体で動いています。入口に受付エージェントを置き、その奥に4つの担当エージェントがいます。

- 受付エージェント: 「何をしたいか」を選択肢で尋ね、担当に振り分ける。自分では原稿を書かず、スキルファイルも読みません
- 企画エージェント: 素材やヒアリングメモから企画書をつくる。参照するスキルは skills/planning/ 配下
- 執筆エージェント: 企画書と素材から原稿を書く。参照するスキルは skills/writing/ 配下
- 校正エージェント: 表記と構成をチェックし、修正済み原稿を出す。参照するスキルは skills/proofreading/ 配下
- レビューエージェント: 人間のフィードバックを学習エッセンスに変える。執筆と校正の両方のスキル（skills/writing/ と skills/proofreading/）を見て最終判断する

読むスキルは記事種別ごとに切り替わります。これに加えて全員が共通で読むファイルが2つあります。表記ルールの regulation-notation.md と、文体ルールの japanese-style.md です。どの担当がどの種別で何を読むかは、skill-loader.md という対応表でまとめています。

受付エージェントは自分では原稿を書きません。「企画を作る」「原稿を書く」「校正する」「レビューする」の4つを選択肢で出して、選んだ番号に応じて担当へ渡すだけです。エージェント名やコマンドを覚えなくても、番号を選べば編集部が動きます。

仕事は工程ごとに次へ手渡していきます。企画エージェントが企画書をまとめ、執筆エージェントが原稿に起こし、校正エージェントが整え、レビューエージェントが最終チェックします。前の担当の成果物がそのまま次の担当の入力になります。各担当は作業を終えると、次に誰へ渡すかを明記して引き継ぎます。たとえば執筆エージェント（ファイル上の名前はハシボソカラス）は、原稿の末尾にこう書いて終わります。

```
━━━━━━━━━━━━━━━━━━━━━━━━
ハシボソカラス ライティング完了
記事種別: {article_type}
次のステップ: オオタカ（校正担当）へ上記原稿を渡してください。
━━━━━━━━━━━━━━━━━━━━━━━━
```

土台にしたのは everything-claude-code というOSSです。これをそのまま使うのではなく、cowork-agents という自分のプライベートリポジトリにフォークして、自社の表記ルールや記事種別に合わせて組み替えています。リポジトリはエージェントの定義（agents/）と、エージェントが読むスキル（skills/）の2つに大きく分かれています。

```text
cowork-agents/
├── agents/
│   └── editorial/
│       ├── editor.md            # 受付エージェント
│       ├── kawasemi.md          # 企画エージェント
│       ├── hashiboso-karasu.md  # 執筆エージェント
│       ├── otaka.md             # 校正エージェント
│       └── shijukara.md         # レビューエージェント（学習も担当）
└── skills/
    ├── shared/
    │   ├── skill-loader.md          # 記事種別→読むスキルの対応表
    │   └── regulation-notation.md   # 表記レギュレーション（全員共通）
    ├── planning/                    # 企画スキル（記事種別ごと）
    ├── writing/
    │   ├── japanese-style.md         # 日本語の文体ルール（全員共通）
    │   ├── owned-media-essay.md      # エッセイ記事の執筆ルール
    │   └── …                         # 記事種別ごとに分かれる
    └── proofreading/                # 校正スキル（記事種別ごと）
```

ファイル名には鳥の名前を使っていますが（執筆エージェントなら hashiboso-karasu.md）、本文では分かりやすさのため役割で呼んでいます。skills/ の下は、企画（planning）、執筆（writing）、校正（proofreading）と工程ごとにディレクトリを分け、さらに記事種別ごとにファイルを分けています。全工程で共通の表記ルールと文体ルールだけは、shared と writing に1つずつ置いて使い回しています。

## なぜ1体にまとめず、役割を分けたのか

最初から5体だったわけではありません。試しに1体のエージェントに企画から校正まで全部やらせたことがあります。前半はそれらしく進むのに、後半になると出力のルールがめちゃくちゃになりました。校正のつもりで書いた文章に、また新しい言い回しのクセが混ざる、といった具合です。工程の境目が曖昧で、どこまでが執筆でどこからが校正なのか、AI自身も見失っていたのだと思います。

役割を分けた理由は2つあります。

1つ目は、処理を順につなぎたかったからです。企画、執筆、校正、レビューは別の作業です。人間の編集部でも担当が分かれています。同じように工程を区切れば、それぞれの担当が自分の仕事だけに集中できます。前の工程の出力が固まってから次へ渡るので、後戻りも追いやすくなりました。

2つ目は、工程ごとに読ませるルールを切り替えたかったからです。各担当は作業の最初に、自分の工程に必要なスキルファイルだけを読みます。執筆エージェントは執筆ルールを、校正エージェントは校正ルールを読み込みます。1体に全部のルールを渡すと、相反する指示が同じ頭の中で混ざります。担当ごとに読むファイルを分けたことで、各工程の判断軸がはっきりしました。

## 執筆エージェントに渡した日本語のルール

執筆エージェントに一番力を入れて渡したのは、日本語らしさのルールです。生成AIは放っておくと、英語の発想に引きずられた文章を書きます。無生物を主語に立てたり、受け身を多用したり、結論を倒置で後ろに飛ばしたりします。読めはするのに、どこか翻訳調になります。

執筆エージェントの定義には、執筆原則として日本語の発想を最初に置いています。実際の記述から抜粋します。

```markdown
## 執筆原則：日本語の発想（英語翻訳調を根から断つ）

英語は「誰がやったか（主体＝モノ）」を主語に立て、日本語は「何が起きたか（出来事＝コト）」を述べる。主体を無理に主語化せず、出来事に視点を置く。細かい文体ルールは skills/writing/japanese-style.md を参照。

- モノ志向よりコト志向：×「彼女がミルクをこぼした」→○「ミルクがこぼれた」／×「私はあなたを理解する」→○「あなたのおっしゃることは理解できます」
- 抽象名詞主語の他動詞構文を節に開く：×「一瞬の熟考があなたに誤りを示す」→○「少し考えれば、間違いだと分かる」
- 所有(HAVE)を存在(ある・いる)に：×「この部屋は窓を二つ持っている」→○「この部屋には窓が二つある」
```

このルールは原稿を直すたびに「なぜこの文を直したのか」を言語化してためたものです。たとえば「この結果は〜を示している」を「この結果から〜が分かる」に直したとき、無生物主語を避けたかったからだと気づきました。そうした気づきを、文体ルールとして1ファイルにまとめています。

執筆エージェントが原稿を書き始める前に読むのは、この文体ルールだけではありません。エッセイ記事の場合、読むのは次の4つです。全員が共通で読むものと、その工程だけが読むものが混ざっています。

| ファイル | 内容 | 読むエージェント |
|---|---|---|
| skills/shared/skill-loader.md | どの記事種別でどのファイルを読むかの対応表 | 全エージェント |
| skills/writing/owned-media-essay.md | エッセイの構成、リード文の型、品質ゲート | 執筆とレビュー |
| skills/shared/regulation-notation.md | 社名やプロダクト名の表記、使わない表現 | 全エージェント |
| skills/writing/japanese-style.md | 英語翻訳調を避ける日本語の文体ルール | 全エージェント |

入口は skill-loader.md です。記事種別を渡すと、そこから「執筆ならこのファイル」と読むべきものが決まります。記事種別ごとにファイルを分けてあるので、エッセイの執筆ルールを直しても、インタビューの執筆ルールには影響しません。

読むファイルのうち、AIっぽさを抜く要になるのが japanese-style.md です。冒頭には、避けたい型を具体例つきで並べています。

```markdown
## 英語翻訳調を避ける

- 無生物主語を避ける。モノを主語にせず、人や事柄を主題にする（例: ×「この結果は〜を示している」→ ○「この結果から〜が分かる」）
- 省ける主語は省く。「私は」「それは」を機械的に置かない
- 受動態を能動に戻す。英語的な受身を、動作主を主語にした能動に直す
- 結論を後ろに置く。倒置や「〜のです」の多用、助詞「と」で文を宙吊りに終える形を避ける

## 文章のリズムと読点

- 同じ主題が続く間は、読点を打たずにつなげる
- 述べる対象が切り替わる境目には読点を打つ
- 長い文で流れを作り、短い文で締める。この長短の落差がリズムになる
```

抜粋なので一部です。ポイントは、抽象的な心構えで終わらせず、×と○の対で渡していることです。「自然な日本語で」とだけ伝えても、AIは平均的な無難さに寄ります。避けたい例を具体的に見せると、同じ書き方を避けて書けるようになりました。

## 校正を、執筆とは別のエージェントにした理由

書いた本人が自分の原稿を直すのは難しいものです。これはAIでも同じでした。だから校正は、執筆とは別の校正エージェントに任せています。書き手の頭をいったん離れて、まっさらな目で原稿を読む役です。

校正エージェントの設計で意識したのは、辛口に徹してもらうことでした。原稿を渡されると、まず表記をチェックします。固有名詞や禁止表現、タイポ、文末のクセなどです。自社の場合、社名やプロダクト名の表記ゆれは特に多いので、ここを機械的に拾えるだけでも助かります。

校正エージェントで重視したのは、出力のルールです。エージェント定義から抜粋します。

```markdown
# Output Rules

- 指摘と修正案は1件ごとに必ずセットで出力する。指摘のみ・修正案のみの単独出力を禁止する
- 確認済み・問題なし・OKの項目は一切出力しない。「確認済み（問題なし）」「問題なし」という見出しや箇条書きは作らない
- 褒める表現は使用しない
```

どれも、私が校正で実際に困った点から決めたルールです。校正のルールづくりで考えたことは、別の記事として Zenn にもまとめています。あわせて読んでもらえるとうれしいです。

関連記事: PRがClaude Codeのエージェントを使ってみた（ https://zenn.dev/takanechi/articles/f9e5fd5ff97165 ）

## レビューエージェントが回す、承認つきの学習ループ

ここまでで原稿は仕上がります。ただ、私がこの編集部で一番つくりたかったのは、この先の仕組みです。レビューエージェントが、私のフィードバックをルールに変えていきます。

校正エージェントの校正が終わると、レビューエージェントが最終チェックをして、私に原稿を見せます。私が「ここはこう直したい」と返すと、レビューエージェントはその指摘を読んで、次から守るべきルールの候補を抜き出します。これを学習エッセンスと呼んでいます。今回の1本を直すだけでなく、同じ指摘を二度しなくて済むように、ルールそのものを育てる発想です。

ここで支えになるのが、ヒューマン・イン・ザ・ループという考え方です。AIの処理の途中に人間の判断を必ず挟む設計を指します。自動化を全部AIに渡しきらず、要所で人間が止めて確認する。レビューエージェントの学習ループは、まさにこの形になっています。

大事なのは、レビューエージェントが勝手にルールを書き換えないことです。学習エッセンスはあくまで提案で、反映するかどうかは私が判断します。提案は決まったフォーマットで出てきます。

```markdown
━━━━━━━━━━━━━━━━━━━━━━━━
シジュウカラ 学習エッセンス提案
━━━━━━━━━━━━━━━━━━━━━━━━
【提案 1】
  対象スキルファイル: skills/{category}/{article_type}.md
  対象セクション: {section}
  変更種別: 追加 / 修正 / 削除
  変更内容:
    現行: {current_text}
    提案: {proposed_text}
  理由: {reason}
━━━━━━━━━━━━━━━━━━━━━━━━
  A. すべて承認 → スキルファイルを自動更新します
  B. 個別に指定
  C. 今回はスキップ
━━━━━━━━━━━━━━━━━━━━━━━━
```

承認すると、レビューエージェントがスキルファイルを更新し、プルリクエストを作ります。

```markdown
## Phase 5: スキルファイルの自動更新

承認を得たら GitHub MCP または filesystem で更新する。

1. mcp__github__create_or_update_file で対象ファイルを更新
2. mcp__github__create_pull_request でPRを作成
3. PRのURLを人間に共有し、マージを依頼する
```

提案には必ず理由が添えてあります。「なぜこのルールが必要か」が書かれていないと、後で読み返したときに判断できなくなるからです。私はPRの中身を見て、納得できれば承認します。承認したものだけが、次の原稿づくりに反映されます。AIが提案し、人間が決めます。この境目を曖昧にしないことが、ルールの品質を守るうえで最も重視した点です。

## 使うほど、自分の現場に馴染んでいく

この編集部を回すようになって、インタビュー記事のライティングは1本あたり約14時間ぶんの工数が空きました。一晩寝かせて読み直す、その翌日を待つ時間がなくなったのが大きいです。空いた時間は、企画や取材そのものに使えるようになりました。

何より大きいのは、使うほど自分の現場に馴染んでいくことです。私が原稿に入れた1回の指摘が、レビューエージェントを通ってルールになり、次の原稿で守られます。最初は平均的な文章を書いていた編集部が、私の判断を取り込みながら、自分の声に近づいていきます。汎用のAIを借りているというより、自分の編集部を少しずつ育てている感覚に近いです。

ひとり広報で、見直しに時間を取られている人は少なくないはずです。同じ悩みを持つ方と、つくり方やつまずきをこれからも共有していけたらと考えています。自分の現場に合ったルールを書き起こすところから、今日からでも始められます。
