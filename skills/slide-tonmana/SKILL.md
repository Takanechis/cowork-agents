# slide-tonmana — 資料トンマナ抽出・指示書セクション生成スキル

このスキルは、ユーザーから渡された既存資料（PDF、PPTX、画像、Figma画像、スクショなど）を解析し、
ユーザーが既に持っている Project指示書に追記するための「トンマナセクション」を生成するための方法論を定義する。

このスキルで扱う資料は PDF または PPTX が前提である。HTML や Web ページのトンマナではない。

## 最終アウトプットの定義

最終的に出すのは、既存の Project指示書に追記する用の Markdownセクション 1 つである。

- ユーザーは既存の指示書を持っているが、内容は Project ごとにバラバラなので共有してもらわない
- そのため最終セクションは、それ単体で意味が通る自己完結型で書く
- 既存指示書のどこに貼っても矛盾しないよう、他の項目との関係を前提にした書き方をしない
- 「上述の通り」「前述の文体に従って」などの参照表現は使わない
- 見出しは `##` から始める（既存指示書の中の 1 セクションとして収まる粒度）
- 単一の `.md` ファイルとして出力する

## 単位とツールの前提（Claude Code 環境）

- 文字サイズの単位は pt で統一する。px は使わない
- テスト生成は python-pptx（PPTX）または reportlab（PDF）を Bash 経由で実行する
- 生成物と最終セクションは Write でファイルに保存し、保存パスをユーザーに提示する
- claude.ai 専用のツール（artifact、present_files）は使わない。代わりに Write でディスク出力する

---

## Step 1：資料の受領と一次抽出

ユーザーから資料を受け取ったら、以下を自分で読み取って抽出する。推測ではなく、資料に実際に表れている値を取る。

### 抽出項目

1. 資料フォーマット情報
  - スライドサイズ（16:9 / 4:3 / A4縦・横 など）
  - ページ余白（上下左右）
  - ヘッダーやフッターの有無と内容（ページ番号、ロゴ位置、日付など）
2. 背景色
  - メイン背景、セクション扉、表紙、本文ページ、図解ページなど用途別に取る
  - HEX値で記載する
3. カラーパレット
  - Primary / Secondary / Accent / Neutral（グレースケール）／ Semantic（成功、警告、エラー、情報）
  - 各色に「いつ使うか」の用途メモを必ず付ける
  - HEX値で記載する
4. フォント
  - 和文フォント、欧文フォント、数字フォント（あれば）
  - PPTX の場合は、そのフォントが標準搭載か、埋め込みが必要かもメモする
  - フォールバック候補を挙げる
5. 文字サイズ、ウェイト、文字色のスケール
  - スライドタイトル、セクションタイトル、本文見出し、本文、キャプション、注釈
  - サイズ（pt）、ウェイト（Regular / Medium / Bold / Black）、行間、文字色をセットで取る
6. レイアウトの粒度
  - タイトルとコンテンツ間の余白
  - 箇条書きのインデントと行間
  - カラム分割のパターン（2カラム、3カラムなど）
  - 図版とキャプションの距離
7. 装飾の特徴
  - 図形の角丸半径、影の有無、罫線スタイル
  - アイコンのテイスト（線画、塗り、フラット、3D）
  - グラフの色使い、凡例位置、データラベル
  - 表組みのヘッダ色、罫線、行高
  - 矢印やコネクタのスタイル
8. 図版や画像の扱い
  - 写真の使用有無とトーン（明るい、落ち着き、モノクロなど）
  - イラストの有無とテイスト
  - 推奨解像度（PDF なら最低 300dpi などの慣行があれば）
9. トーン（言語面）
  - 文体、語尾、専門用語の出し方、記号の使用有無
  - 1 スライドあたりの情報量の傾向（密か疎か）

抽出後、読み取った内容をユーザーに見える形でまとめて提示する。

## Step 2：曖昧点のヒアリング（最重要）

Step 1 で抽出した結果のうち、以下に該当するものは必ずユーザーに確認する。勝手に決めない。

- 同じ用途で複数の値が観測されたもの
- サンプル数が少なくて一般化できないもの
- 用途が不明な色
- 資料に明示されていないが、Project 全体で必要になるであろう要素
  - 例、表紙レイアウト、目次、章扉、エラーや注意喚起の色、出典や脚注のスタイルなど
- PDF や PPTX 固有の確認事項
  - PPTX 前提か、PDF 前提か、両方か
  - 提出先（クライアント、社内、投資家など）による使い分けの有無
  - 既存テンプレート（.potx、マスタースライド）の有無

ヒアリングは箇条書きで番号を振って一度にまとめて聞く。1 問ずつ往復するとユーザーの負担が大きくなる。

ヒアリングの例:

```
確認させてください。
1. スライドタイトルが 32pt と 28pt の 2 種類観測されました。表紙が 32pt、各スライドが 28pt という理解で合っていますか。
2. #FF6B35 というオレンジが 1 箇所だけ使われていました。これはアクセントとして恒常的に使うものですか、特定資料の例外ですか。
3. 提出先によってトンマナを変える必要はありますか。
4. 既存の PPTX マスタースライド（.potx）はありますか。あれば、それを基準にして良いですか。
```

## Step 3：テスト生成と確認

ヒアリングの回答を得たら、実際にその指示書通りに資料を作って見せる。

- 形式は想定アウトプットに合わせて PPTX または PDF を実際に生成する
  - PPTX 前提なら python-pptx で .pptx を作成する
  - PDF 前提なら reportlab（または同等）で .pdf を作成する
  - 両方ある場合は PPTX を優先する（後で PDF 化できるため）
- 内容はユーザーの業務に近い仮テーマで、表紙、本文 1 スライド、図表 1 スライド、章扉の計 4 ページ程度を作る
- 生成したファイルは Write でディスクに保存し、保存パスをユーザーに提示する

サンプルを見せた後、必ず次のように聞く。

- このトンマナで進めて問題ないですか
- 開いてみて違和感がある箇所（色がきつい、フォントが意図と違う、余白が窮屈など）があれば、具体的に「ここの○○が△△すぎる」と教えてください
- 修正してもう一度生成します
- OK であれば、最終的な指示書セクションを出力します

ユーザーから「OK」「問題ない」「これで」などの明確な合意が出るまで、最終セクションは出力しない。
修正要望があれば Step 3 をループする。

---

## Step 4：最終指示書セクションの出力

ユーザーの OK が出たら、既存指示書に追記する用の Markdownセクションを出力する。
単一の `.md` ファイルとして Write で保存し、保存パスを提示する。

ユーザーの既存指示書がどんな構成でも違和感なく入るよう、自己完結型で書く。

### 最終セクションに必ず含める要素

- 他のセクションを参照せず、外部前提を置かない自己完結型である
- コピペでそのまま使える python-pptx と reportlab の定数定義を含む
- 「やってはいけないこと」の禁則リストを含む
- 判断に迷ったときのデフォルトルールを含む
- 文体は「である調」または指示形（「〜すること」「〜する」）で統一する

## 重要な原則

- 既存指示書は受け取らない。ユーザーごとにバラバラなので見ない。出力は単独で意味が通る形にする
- 推測で埋めない。資料に無い情報は必ず聞く
- テスト生成を飛ばさない。実際に PPTX や PDF を生成してユーザーに確認してもらう
- OK なしで完成させない。「これで指示書を確定します」とユーザーが明示するまで Step 4 に進まない
- 最終出力は 1 ファイルの Markdown とする。既存指示書に追記する想定で書く
- 単位は pt とする。PDF や PPTX 前提なので px は使わない
- 特に指定がなければ日本語で進める

## このスキルの禁則

- claude.ai 専用ツール（artifact、present_files）を前提にした手順を書かない
- 「トーン&マナー」という表記を使わない。「トンマナ」で統一する
- 資料に無い値を観測値として書かない。観測できなかった項目はヒアリングに回す
- ヒアリングを 1 問ずつ往復しない。番号付きで一度にまとめて聞く
