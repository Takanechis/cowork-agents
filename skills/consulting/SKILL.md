# コンサルティングスキル: 要件定義・仮説構築

## Overview

目的: 抽象的な課題や依頼を受け取り、「問い→情報収集→仮説→構造化ドキュメント」の流れで意思決定を支援する。

対象: プロジェクト要件定義、施策設計、戦略立案、課題分析など、論点が曖昧な状態からスタートする全ての検討。

---

## ワークフロー

### Phase 1: 問いの設計

**目的**: 抽象的な課題を「答えるべき問い（Issue）」に変換する。

手順:
1. ユーザーから提示された課題・状況をそのまま受け取る
2. 課題の背景にある「本当に解くべき問題」を推定する
3. その問題を解くために「問うべき問い」を 3〜5 個設計する
4. 各問いに優先順位をつけ、「なぜこれを問うのか」を一行で示す

問いの設計基準:
- Yes/No で終わらず、「なぜ」「どうすれば」「何が」で始まるか
- 答えが出たとき、意思決定が変わるか
- 現実的に答えられる範囲か（情報が存在するか）
- 問い同士の関係性（上位・下位・並列）が整理されているか

出力形式:
```
## 解くべき問い

### 背景認識
（課題の構造・前提の解釈を 3〜5 行で示す）

### 問いの一覧

| 優先 | 問い | 設計理由 |
|---|---|---|
| 1 | ～か？ | ～だから |
| 2 | ～か？ | ～だから |
...

### 最優先の問い
（1つに絞り、次フェーズで深掘りする問いを明示する）
```

### Phase 2: 情報収集（人間への質問）

**目的**: 仮説を立てるために不足している事実・数字・文脈を人間から引き出す。

手順:
1. Phase 1 の最優先の問いを仮説化するために「何が分かれば仮説が立てられるか」を列挙する
2. 不足情報を「事実確認」「判断軸の確認」「制約条件の確認」の 3 種に分類する
3. 1 回あたり最大 5 つの質問に絞って人間に投げる
4. 回答を受け取ったら、まだ不足があれば追加質問する（最大 2 ラウンド）

質問の書き方ルール:
- 質問の意図（なぜ聞くか）を一行で添える
- 選択肢がある場合は「A / B / C のどれに近いですか」と選択肢を提示する
- 数字・固有名詞・時期など、具体的な回答を引き出せる聞き方にする

出力形式:
```
## 情報収集

次の仮説を立てるために、以下を確認させてください。

**仮説化したい問い**: ～

### 質問

**Q1（事実確認）**: ～
→ 聞く理由: ～

**Q2（判断軸の確認）**: ～
→ 聞く理由: ～

**Q3（制約条件の確認）**: ～
→ 聞く理由: ～
```

### Phase 3: 仮説構築

**目的**: 収集した情報をもとに、問いへの暫定的な答え（仮説）とその論拠を構造化する。

手順:
1. 各問いに対して「仮説（暫定の答え）」を 1〜2 文で言い切る
2. 仮説を支える論拠を「事実」「推論」「前提」に分けて列挙する
3. 仮説が崩れる条件（反証可能性）を明記する
4. 仮説間の関係を「上位仮説 → 下位仮説」の形で整理する
5. 「最も優先すべき打ち手の方向性」を 1〜2 行で結論づける

出力形式:
```
## 仮説マップ

### 中心仮説
（問いへの暫定回答を 1〜2 文で言い切る）

### 論拠の構造

**事実**（確認済みの情報）:
- ～

**推論**（事実から導いた解釈）:
- ～

**前提**（検証できていないが置いている仮定）:
- ～

### 反証条件
（これが分かったら仮説を修正すべきという条件）
- ～

### 下位仮説
（中心仮説を構成するサブ仮説）
1. ～
2. ～

### 結論（打ち手の方向性）
（仮説から導かれる行動指針を 1〜2 文で）
```

### Phase 4: ドキュメント出力

**目的**: Phase 1〜3 の成果を、意思決定者が読める構造化ドキュメントとして出力する。

ドキュメント構成（標準）:
1. **エグゼクティブサマリー** — 課題・問い・結論を 5 行以内で要約
2. **背景と課題の定義** — 何が問題で、なぜ今解くのか
3. **解くべき問いの設計** — Phase 1 の出力を整理
4. **仮説とその論拠** — Phase 3 の出力を整理
5. **推奨アクションと優先順位** — 具体的な次の一手
6. **残論点と確認事項** — まだ検証できていないこと

出力ルール:
- Markdown で出力する（`**` による太字は使用しない）
- 見出しは `##` `###` を使う
- 仮説・論拠・アクションは箇条書き、説明文は散文で書き分ける
- 「推測」「仮説」「要確認」はラベルを明記する
- 断言できないことを断言しない（「〜と考えられる」ではなく「仮説: 〜」と書く）

## 品質ゲート

- 問いが「意思決定を変えうる」ものになっているか
- 仮説が「言い切り」の形になっているか（「かもしれない」で終わっていないか）
- 論拠が「事実」「推論」「前提」に分類されているか
- 反証条件が明記されているか
- 推奨アクションが具体的な動詞で始まっているか
- 禁止表現が 0 件か（regulation-notation.md 参照）
