# proposal-slide: 判断を求める提案資料をスライドにする

## このスキルの位置づけ

提案の中身を、読み手が判断を下せるスライドに組み立てる。
基準は説明の網羅性ではなく、判断の速さと正確さに置く。

スライドは「起案資料の見せ方」であり、論理そのものは起案資料スキルが正本になる。
本スキルは、その論理をスライドという形式に移すときの手順と規範を定める。

| 正本 | 扱う内容 | 本スキルとの関係 |
|---|---|---|
| `skills/consulting/proposal-deck.md` | 起案資料の論理、節立て、参考資料 | 中身を作る段階で従う。ブランチ上に無いときは次の行を使う |
| `mf-video:decision-proposal-deck` | 判断点の分け方、根拠の地位、提出前の点検 | 中身を作る段階で従う |
| `skills/shared/regulation-notation.md` | 表記、固有名詞、禁止表現 | スライドの文言にも全文適用する |
| `~/.claude/skills/japanese-tech-writing/SKILL.md` | 論証の厳密さ、冗長の排除、LLM口調の禁止 | 文言と話し手メモに適用する |
| `skills/writing/japanese-style.md` | 翻訳調の排除、リズム | 文言と話し手メモに適用する |
| `mf-video:natural-japanese` | AIっぽさの除去 | 書き終えたあとの推敲に使う |
| AtomicSoftware Slide Design System | 色、書体、余白、部品 | 見た目はここに従う。表記だけは regulation-notation を優先する |

規範が食い違ったときの順位は、regulation-notation、japanese-style、japanese-tech-writing、本スキル、外部記事の順とする。

## 学習元の記事と、採用した原則

7本の記事から次を採った。自社の規範と食い違う点は「採用しない」に書く。

### rakko_inc の見せ方編から採用したもの

- 冒頭の2枚で、聞いたあとの状態と全体像を示す
- 判断を求める章の頭で現在地を示す。目次を再掲し、今の章だけ残して他は薄くする
- 答えを後回しにするときは「あとで説明する」と先に約束し、必ず回収する
- 1スライド1メッセージ。収まらなければ枚数を増やす。疲れさせるのは枚数ではなく1枚の情報量
- 各スライドの下部に持ち帰りの1行を置く。聞いていない人が後から見ても要点が拾える
- 情報の構造からレイアウトの型を機械的に決め、型の種類を絞って繰り返す
- 色数を増やさない。強調の手段に役割を割り当て、強調のインフレを防ぐ
- 表紙と締めだけ背景を変える。締めは要約ではなく行動の依頼にする

採用しないもの。

- 要素の個数を見出しに入れる。自社では見出しに個数を入れない。個数はカードの枚数で見せる
- 絵文字を機能として使う。自社では絵文字を使わない。順位や現在地は数字と図形で示す
- マスコットを全ページに置く。装飾はブランドの4つのアトムに限る

### tokium_dev のストーリーと視線誘導から採用したもの

- 導入で「何を話すか」「なぜ話すか」「何を持ち帰るか」を示し、まとめの主張と飛躍なくつなぐ
- 本題には、導入からまとめまでの筋に乗る話題だけを置く
- 生成AIは発表者の主張と、どの文に知見が込められているかを知らない。筋と強調箇所は人間が教える
- 1枚の視線は、配置、語の選び方、強調の3つで誘導する。左上から右下へ流す
- レイアウトの型を事前に用意し、出力のぶれを減らす
- 完成したら通し読みし、違和感が消えるまで直す

採用しないもの。

- キーメッセージ13文字、1枚105文字の目安。結論を書く見出しには収まらない。自社の目安は Step 3 の「文字量の目安」で画面幅から決め直した

### オクトの説明の仕方から採用したもの

- 前提を示し、自分と相手の情報の差を埋めてから本題に入る
- 一文を短くする。相手が一度に処理できる量には限りがある
- 結論を先に置き、承認を求めるのか相談なのかを最初に言う
- 説明は双方向で進める。どこまで伝わったかを確かめ、詰まった箇所を埋める

### Goodpatch のプレゼン設計から採用したもの

発表の設計と場の運び方に関する記事で、見た目のルールではない。

- 依頼の背景を先に確かめる。なぜ頼まれたのか、何を出せば目的を達成するのか、自分の所属に何が求められているのか
- 骨子は1人でまとめ、全社に関わるなら経営陣に、プロダクトの話なら PM とデザイナーに、スライドを書く前に見てもらう
- 冒頭でゴールを示す。聞き終えたときに何が決まっているかを共有する
- 役員向けは資料の説明を10分で終え、残りを対話に充てる。資料の順に縛られず、相手の論点に合わせて枚を飛ぶ
- 相手の呼吸に合わせる。ペースと熱量を相手に合わせる
- 終了後に反応を聞き、次の資料に反映する

採用しないもの。

- 冒頭の雑談で関心を引く。判断を求める資料では、冒頭は判断と推奨に使う
- 体験と議論のパートを必ず入れる。位置づけがワークショップのときだけ入れる

### デジタル庁の実践ガイドブックから採用したもの

ダッシュボードの設計書だが、図表と数字の見せ方は提案スライドに通じる。
Power BI のテンプレートとポリゴンデータは当社では使わないので採らない。

- 全体を把握する数字を先に、詳細のグラフを後に置く。優先度の高い情報ほど目立つ場所に置く
- 左上から右下へ読む動線に沿って配置し、全体像は上か左に、詳細は下か右に置く
- 16:9 を 2〜6 分割するグリッドで要素の大きさと位置をそろえる
- グラフは目的で選ぶ。単一の重要な値は大きな数字、正確な値の確認は表、推移は折れ線、項目の比較は棒、構成比は円。円は細かい比較に使わない
- 棒グラフと面グラフの基準値は 0 から始める。軸の途中を省略して差を誇張しない
- 目標値、平均値、前年値のような比較の基準を図表の中に示す
- 項目の並びに意味を持たせる。大きさ順、時系列、五十音順のいずれかにし、無作為に並べない
- 不要な線、枠、目盛りを消す。3D、影、装飾の図柄を使わない
- 図形と背景のコントラスト比は 3:1 以上、文字は 4.5:1 以上にする
- 色だけで意味を伝えない。ラベルや形でも区別できるようにし、色覚の多様性を確かめる
- 図表のタイトルに内容とデータの範囲と期間を書く。単位、出典、更新日、定義、注記を添える。略語は避けるか説明する
- 凡例とラベルは図表の近くに置き、離さない
- 作る手順は、要件整理、プロトタイプ、合意形成、実装と点検の順。プロトタイプで関係者の合意を取ってから作り込む

採用しないもの。

- 7色のカラーパレットと増減のセマンティックカラー。自社は Black と Silver を主にし、アクセントは Orange の1色に限る。増減は色ではなく矢印と語で示す
- 1〜5色の範囲。自社は3色までとする

### virtual-planner のデザインの基本原則から採用したもの

- 伝わる資料の評価は、瞬時に分かるかと、ルールが決まっているかの2点で行う
- 使う色は文字色、メインカラー、アクセントカラーの3色まで。役割を固定し、枚ごとに強調色を変えない
- 配色の比率は背景 70、メインカラー 25、アクセント 5 を目安にする
- 色を増やしたくなったら、先に明度と彩度の違いで対応する
- 英数字は和文書体で組まず、欧文書体を使う
- 複数の要素は Z の順に読まれる前提で置く
- 余白を取る。余白が無いと階層が読めず、窮屈になる
- 単語の途中で改行しない。区切りのよい位置で改行を調整する
- 整列と近接。位置とサイズをそろえ、関連する要素は近くに、無関係な要素は離す。ずれ、はみ出し、不等間隔、サイズの不統一をなくす
- 書式はマスターに保存して全枚で一貫させる。自社では deck.json の faces と枚の雛形がそれにあたる
- 表はタイトル行と列をセルの色と文字で区別し、セルのサイズと余白と文字の寄せを統一し、目立たせる箇所だけ色か枠で強調する
- グラフは強調する系列だけメインカラーかアクセントにし、他はグレーの濃淡で描く。目盛りは最小限にし、詳細な値はデータラベルで示す。項目と数値を詰め込まない

採用しないもの。

- メイリオ、游ゴシック、ヒラギノの指定。自社の書体は IBM Plex Sans JP と IBM Plex Sans
- アクセントはメインカラーの補色。自社は Orange #FF4600 に固定
- 行間 1.1〜1.2。自社の本文は 1.5

## Step 0: 入力を判定する

受け取ったものが次のどちらかを判定し、入口を分ける。

| 入力 | 判定の目安 | 入る手順 |
|---|---|---|
| 完成済みの起案資料 | 求める判断、推奨案、根拠、次の行動が本文にそろっている Markdown | Step 1 の確認だけして Step 2 へ |
| 粗い素材 | メモ、文字起こし、箇条書き、口頭の依頼 | Step 1 から |

完成済みの起案資料でも、Step 1 の「提案の芯」と「資料の型」は決める。
省けるのは、芯と型が起案資料に書いてあるときだけとする。
求める判断が本文から読み取れないときは Step 1 を全部やり直す。

入力に無い事実を補わない。不足は確認事項として書き出す。
依頼の背景も確かめる。なぜ頼まれたのか、何が出れば目的を達成するのか。

## Step 1: 判断と推奨を固める

スライドを書く前に、提案の芯を次の形で一文に書き、ユーザーに確認する。

```
決めたいのは［判断］である。推奨は［案］で、理由は［決め手となる2〜3点］。
主なリスクは［リスク］で、［対策］で抑える。承認されれば［次の行動］に進む。
```

あわせて次を決める。

1. 読む相手と最終的な決裁者
2. 今回の場で求める判断。承認か、方向性の合意か、意見の収集か
3. 提案全体の中での今回の位置づけ。キックオフ、ワークショップ、中間報告、最終報告のどれか
4. 推奨する案と、現実的な代替案。何もしない案も含める
5. 判断の基準と制約
6. 範囲外と明示するもの
7. 承認後に始まる行動
8. 起案資料の日付が本日より過去のときに、そのまま使うか直すか

### 資料の型を選ぶ

読み手と場の性質で3つの型を使い分ける。

| 型 | 向く場面 | 構成 |
|---|---|---|
| 論点分解型 | PJT 内の詳細な検討。複数の論点があり、比較表で決着させたい | サマリ、発端、論点の分解、論点ごとの比較と結論、最終結論、懸念と対処、次のアクション |
| Why What How 型 | 役員向けの承認依頼。判断の速さが優先 | Why は課題、What は承認してほしい2〜3点、How は運用の具体。箇条書き中心の体言止め |
| 判断点ごとの節立て | PJT 内の承認依頼。判断点が複数あり、それぞれに根拠を見せたい | 冒頭2枚で判断と推奨を先に出し、本題は上流の判断から下流の判断へ節を立てる。各節の末尾でその判断の結論を再掲する |

承認依頼に論点分解型を当てると、章の相互参照と表の多用が読み手の負荷になる。
逆に詳細検討に Why What How 型を当てると、比較の根拠が薄くなる。
役員向けの場では、資料の説明は10分で終える前提で枚数を組む。

### 根拠の地位を明示する

主張ごとに、根拠の地位を4区分で持つ。スライドでは注記か出典欄に書く。

| 区分 | 内容 |
|---|---|
| 事実 | 検証済みの測定値、顧客の記録、確認済みの運用上の制約 |
| 観察 | 繰り返し確認できているが、母集団を代表するとは言えない根拠 |
| 仮説 | もっともらしい説明や見通しだが、検証が必要なもの |
| 未確認 | 決める前に必要な情報 |

資料に書かれていない事柄を確定事実として書かない。
複数の資料の記述を接続して1つの事実に見せない。
実施時期が未定なら日付を書かず、順序だけを示す。
起案資料の数字がその資料内で食い違うときは、起案資料の表現をそのまま使い、確認事項として README に書く。

### 確認が取れないときの扱い

非同期の作業やサブエージェントでの実行では、Step 1 と Step 2 の確認が返ってこない。
そのときは仮の答えを置いて進め、聞くはずだった質問と置いた仮の答えを `drafts/deck-<slug>/README.md` の「確認事項」に一覧で残す。
仮の答えは、起案資料の記述を優先し、資料に無い事実は足さない。

## Step 2: ストーリーを組む

スライドに落とす前に、構成表を作ってユーザーに確認する。
1行が1枚に対応する。

| 枚 | 役割 | 結論を書いた見出し | 載せる内容と根拠 | 型 | 持ち帰りの1行 | 話し手メモ |
|---|---|---|---|---|---|---|

### 標準の並び

| 位置 | 役割 | 内容 |
|---|---|---|
| 1 | 表紙 | タイトルは結論を含む。日付、起案者、位置づけ |
| 2 | 判断と推奨 | 何を決めるか、推奨は何か、承認か相談か |
| 3 | 全体像 | 目次。以降の各枚はここに対応させる |
| 本題 | 判断点ごとの節 | 前提、課題と目的、提案内容、選択肢と比較、根拠、期待効果と測定、リスクと対策、実行計画 |
| 締め | 決めていただきたいこと | 判断項目の再掲と、承認後の次の行動 |

位置づけによって本題を削る。
キックオフなら提案内容から実行計画までを薄くし、最終報告なら前提と課題を確認にとどめる。

### 組むときの規則

- 各枚は目次のどれかに対応する。対応しない枚は削る
- 判断点が複数あるときは、上流の判断を先に、下流を後に置く。共通の前提は一度だけ書く
- 冒頭で触れた課題の答えを後の枚で出すときは、冒頭の枚に「〇〇の枚で説明する」と書く
- 目次の再掲は、判断を求める章の前だけに挟む。前提、スケジュール、別論点の前には置かない。今の章だけ残し、他は薄くする。5秒で流す枚なので文は置かない
- ページ番号は「n / 全体」の形にする
- 締めの枚は要約にしない。判断項目と、承認されたら誰が何をするかだけを置く
- 見出しは話題のラベルではなく結論を書く。見出しだけを順に読んで主張が伝わる状態にする
- 見出しに個数を入れない。「2つの課題」ではなく、課題の中身を見出しに書く
- 起案資料の節番号とスライドの節は一対一にならなくてよい。ただし話し手メモで起案資料の節を引くときは「起案資料の第3節」と資料名を添える

### 起案資料の節をスライドに移す規則

起案資料には、判断に直接つながらない節が含まれる。
次の規則で降ろす。

| 起案資料の節 | 扱い |
|---|---|
| 本日の判断に影響しない前提の表 | 独立した枚にしない。関係する枚の注記か、別論点の枚の根拠として1文にする |
| 検討の過程を示す表。バリュープロポジションキャンバス、比較の全表 | 結論の交点だけを枚に残し、表そのものは話し手メモか参考資料に降ろす |
| 行数の多いスケジュール表 | 8行以内に統合する。判断に関わる節目と、新しく増える工程だけを残す |
| 本日は決めない別論点 | 1枚にまとめ、見出しに「本日は決めない」ことと、いつ判断を求めるかを書く |
| 取れなかった情報の一覧 | 枚にしない。確認事項として README と、関係する枚の注記に書く |

## Step 3: 1枚の情報を設計する

### 1枚1メッセージ

1枚で伝えることは1つにする。
2つ以上あれば枚数を分ける。
聞き手にお願いする行動は、1枚につき2つまでにする。

### 構造から型を決める

情報の構造が決まればレイアウトの型も決まる。
型の種類を絞り、同じ型を繰り返す。
聞き手は型を学習し、後半ほど読む負荷が下がる。

| 情報の構造 | 型 | 例 |
|---|---|---|
| 並列の要素 | カードの横並び。3枚か4枚 | 課題の一覧、選択肢の一覧、お願いの一覧 |
| 対応関係 | 表 | 現状と提案後、選択肢と評価軸、用語の対応 |
| 時系列 | タイムライン | 実行計画、配信スケジュール |
| 階層 | ツリー図 | 論点の分解、目標の要素分解 |
| 数値による説得 | 大きな数字のカード | 問い合わせ数、商談化率、ROI |
| 推移 | 折れ線 | 月ごとの配信数、利用率の変化 |
| 項目の比較 | 棒グラフ | 案ごとの費用、セグメントごとの院数 |
| 構成比 | 円。項目は4つまで | プランの内訳 |
| 因果 | 連関図 | 悪循環と好循環 |
| 流れ | フロー図 | ファネル、業務の流れ |
| 1文で足りる主張 | メッセージ1行の枚 | 判断と推奨、章の結論 |

数値は文章に埋め込まず、大きな数字として独立させる。
数字の下に、分母と出典と時点を小さく添える。

### 図表の規則

- 全体を示す数字を先に、詳細を後に置く。1枚の中でも左上に全体、右下に詳細
- 棒グラフと面グラフの基準値は 0 から始める。軸の途中を省略しない
- 目標値、前年値、平均値のような比較の基準を図表の中に線か注記で示す
- 項目の並びは大きさ順、時系列、五十音順のどれかにする
- 不要な線、枠、目盛りを消す。詳細な値はデータラベルで示す
- 図表の見出しに、内容とデータの範囲と期間を書く。単位、出典、時点、定義を注記に添える
- 凡例は図表の近くに置く。系列が2つまでなら凡例を使わず、線の端にラベルを置く
- 表はタイトル行をカード面の色と太字で区別し、セルの余白と文字の寄せを統一する。行は8行まで、列は4列までを目安にする
- 強調する系列だけ Orange にし、他は Silver の濃淡で描く

### 視線を誘導する

- 左上から右下へ読む順に置く。「今まで」と「これから」のように位置づけの異なる内容を同じ図形で並べない
- 複数の要素は Z の順に読まれる前提で置く
- 図表には読み方を示す見出しをつけ、強調すべき場所を1か所だけ示す
- 矢印の形と色は1種類にそろえる
- 要素は4つまでを目安にする。5つ以上なら枚を分けるか、表にする
- 関連する要素は近くに、無関係な要素は離す。カードの幅、間隔、上端をそろえる
- 単語の途中で改行しない。見出しが2行になるときは、意味の切れ目で `<br>` を入れる

### 持ち帰りの1行を残す

スライドには見出しと要点だけを書き、説明は話し手メモに置く。
ただし各枚の下部に、その枚の結論を1行で置く。
発表を聞いていない人が後からスライドだけを見ても、要点が拾える状態にする。

### 文字量の目安

画面幅 1664px に 52px の見出しを置くと、1行は 32 文字で折り返す。
目安はそこから決める。

| 要素 | 目安 |
|---|---|
| 見出し | 32 文字以内で1行。結論を優先し、超える場合は意味の切れ目で2行まで。64 文字を超えたら枚を分ける |
| 本文。カード、表、図の中の文字の合計 | 200 文字以内。表の枚は適用外とし、代わりに 8 行 4 列の上限を守る |
| 持ち帰りの1行 | 50 文字以内 |
| 注記と出典 | 60 文字以内 |

本文に数えるのは、見出し、持ち帰りの1行、注記、ページ番号、話し手メモを除いた可視文字とする。
数え方は Step 7 の機械検査にある。
目安を超えたときは、例やテロップ案を話し手メモに降ろす。
機械的に削って意味を落とさない。

## Step 4: 配色とトンマナ

見た目は AtomicSoftware Slide Design System に従う。
https://claude.ai/artifact/8i2kJMwzZosAxYG1YakaVc

生成の前に `project/README.md` と `project/colors_and_type.css` を読み、トークンをそのまま使う。
ファイルの一覧は `scope: "files"` で取り、パスを推測しない。
Slides 型の作成結果は `project/api/tokens.md` と `project/tokens.json` を読むよう指示するが、このデザインシステムには両方とも無い。
その2件は読まずに進め、テーマメニューには反映されない前提で色の値を直接書く。

### 色

| 役割 | 値 | 用途 |
|---|---|---|
| 背景 | #F4F4F4 | 本文の枚の標準背景 |
| カード面 | #FFFFFF | カード、表の背景、表のタイトル行 |
| 本文の文字 | #202222 | 見出しと本文 |
| 補助の文字 | #616565 | 注記、出典、分母、小見出し |
| 薄い文字 | #9EA2A2 | 目次の再掲で今の章以外を薄くするとき |
| 区切り線 | #BBBDBD | 表の罫線、カードの枠 |
| 非強調の面 | #D7D9D9 | 対象外のセル、グラフの非強調の系列 |
| 暗い背景 | #202222 | 表紙と締めの2枚だけ |
| アクセント | #FF4600 | 1枚に1つの役割。推奨案の枠、強調する数字 |
| 暗い背景上のアクセント文字 | #FA9169 | 表紙と締めの強調 |

規則。

- 1枚は背景、文字、アクセントの3色まで。Silver の濃淡は数えない
- 配色の比率は、背景とカード面が 70、Black と Silver が 25、Orange が 5 を目安にする
- Orange は塗り、罫線、番号の図形、48px 以上の太字の数字にだけ使う。白地で 3.4:1 しかなく、本文の文字には使えない
- 文字と背景のコントラスト比は 4.5:1 以上、図形と背景は 3:1 以上にする。#616565 の白地は 5.9:1、#9EA2A2 は 2.6:1 なので、#9EA2A2 は薄くする目的以外に使わない
- 色だけで意味を伝えない。対象と対象外、推奨と代替は、枠の太さかラベルでも分かるようにする
- 表紙と締めの2枚だけ暗い背景にし、間は明るい背景にする。始まりと終わりが言葉なしで伝わる
- グラフの系列は Silver の濃淡で描き、Orange は1系列の強調だけに使う
- 影、グロー、グラデーションの背景、ガラス風の半透明、3D は使わない。奥行きは余白で作る
- 角丸は原則 0。曲線はアトムの図形からだけ生まれる
- 装飾はブランドの4つのアトムに限る。アイコンは Black と Silver の2色
- ロゴは `project/assets/logo-wordmark.png` を使う。暗い背景の枚では `filter: invert(1)` で白反転する

### 強調の役割

強調の手段に役割を割り当て、役割の外で使わない。
全部が太字なら何も強調されていないのと同じになる。

| 手段 | 役割 |
|---|---|
| Orange の枠 | 推奨案、その枚で決めてほしい項目。同じ役割の要素が複数あれば全部に付けてよい |
| Orange の大きな数字 | その枚の決め手になる数値。1枚に1つ |
| 太字 | 見出し、持ち帰りの1行、表のタイトル行 |
| 背景の反転 | 表紙と締め |

「1枚に1か所」は「1枚に1つの役割」と読む。
推奨案が2つのセグメントに同時にまたがるときは、両方に Orange の枠を付けてよい。
別の役割、たとえば推奨案の枠と強調の数字を同じ枚に置かない。

### 書体とサイズ

単位は px で書く。
Slides 型は 1920 × 1080 の px で組み、24px 未満の文字を受け付けない。
デザインシステムの caption 14px と eyebrow 12px は使えないので、24px に引き上げる。

| 要素 | 書体 | サイズ |
|---|---|---|
| 和文 | IBM Plex Sans JP | Regular 400 と Bold 700 の2ウェイト |
| 欧文と数字 | IBM Plex Sans。大きな数字とページ番号は IBM Plex Mono | 同上 |
| 表紙のタイトル | Bold | 72px |
| 枚の見出し | Bold | 52px。行間 1.25 |
| 小見出し。章名と現在地 | Regular、#616565 | 24px。字間 2px |
| 本文 | Regular | 26〜30px。行間 1.5 |
| 持ち帰りの1行 | Bold | 28px |
| 注記、出典、ページ番号 | Regular、#616565 | 24px |
| 大きな数字 | Mono Bold | 80〜120px。行間 1.1 |

見出しと本文の比は 1.7〜2.0 倍にする。
英数字は和文書体で組まず、`font-family` の先頭に IBM Plex Sans を置く。

### 余白とグリッド

- 16:9、1920 × 1080 で作る
- 枚の内側の余白は四辺とも 128px。本文に使える面積は 1664 × 824
- 持ち帰りの1行は `position:absolute; left:128px; bottom:176px; width:1664px` に置く
- フッターは `position:absolute; left:128px; right:128px; bottom:64px` に置き、左に出典、右にページ番号を入れる
- y が 920px より下に、フッター以外の要素を置かない。本文の `padding-bottom` は 240px にして持ち帰りの行と重ねない
- 枚の面積の 20〜30% を空けたままにする。余白は削る対象ではなく設計の対象とする
- 2カラムの比は 62:38。カードの横並びは `gap: 32px`
- 要素の大きさと位置は 2〜6 分割のグリッドにそろえる。ずれ、はみ出し、不等間隔、サイズの不統一をなくす

### 表記の例外

デザインシステムの README は製品名を「MedicalForce」と書いているが、自社の正本は `medicalforce` と小文字始まり一単語で定める。
同じ README はミッションを「日本の産業全体を底上げする」と書いているが、自社の正本は「未来に、もっと余白を。」とする。
スライドの文言は regulation-notation を優先する。
社名は「アトミックソフトウェア株式会社」、英語では「AtomicSoftware Inc.」とする。

## Step 5: 文言の規範

スライドの文言と話し手メモは、日本語ライティングの規範を全文適用する。
ここでは、スライドで特に出やすい違反だけを挙げる。

### 文の形

- 見出しは結論を書く。体言止めか言い切りにする
- カードの中身は短い名詞句か体言止め。文末の「です」「ます」はカード内では省く
- 話し手メモはですます調で、一文を短くする。長い文は述べる対象が切り替わる位置で分ける
- 一文に1つの情報。「議論の経緯、アンケート結果、企画担当との調整」を一文に詰めない
- 「でも」「しかし」「ですが」で始めない。課題も改善につながる表現で書く
- 略語は避けるか、初出で正式名を書く

### 使わない表現

- 根拠なき修飾語。画期的な、革新的な、唯一無二の
- 強調語。一切、完全に、非常に、極めて
- 比喩。スポーツ由来の表現、「入口」「土台」「ブレーキ」のような役割の比喩
- 比喩動詞。「回っている」「化ける」「刺さる」「効いている」「走らせる」「転がす」「回す」。「運用している」「受注に至る」「反応がある」「続けている」のように、起きていることをそのまま書く
- 「させていただく」の多用。資料全体で2回まで
- 並列の列挙に「・」を使う。「や」「と」「、」で表す
- 「——」「ーー」「―」で語句をつなぐ
- 語句の直後に括弧で補足を付ける。「（仮）」「（予定）」も同じ。補足は注記として独立させる。曜日の「（火）」だけは許す
- 言葉同士を「＝」でつなぐ
- 絵文字、感嘆符、文末のコロン
- 「まず」を言い出し語として使う。時系列の始まりにだけ使う
- 曖昧語。「そこそこ」「一概には言えない」「基本的には」「おおむね」「かなり」
- 疑似具体語。手触り、肌感、温度感、熱量、解像度を上げる、腹落ち
- LLM口調。「重要なのは〜である」「〜と言えるでしょう」「多角的に」「〜に他ならない」
- 「〜にあたる」「〜となる」「〜という形」の言い換えとしての使いすぎ

起案資料にこれらの語があっても、スライドでは言い換える。
言い換えた語は README の「確認事項」に元の語とともに書く。

### 数字と出典

- 「多い」「少ない」は数字にする。「順調」ではなく進捗率で書く
- 数字には分母、時点、出典を添える。下限や上限として扱う数字は、その旨を注記する
- 「価値がある」と広く言わず、幅を持った見積もりか定性的な根拠を示し、不確かさを書く
- 日付が未定なら書かない。順序だけを示す

### 固有名詞

- 社名、製品名、氏名、役職は regulation-notation の表に従う
- 氏名は姓と名の間に半角スペース。役職と氏名は「／」で区切る
- ミッションは「未来に、もっと余白を。」と句点まで含める

## Step 6: 生成する

標準の出力は claude.ai の Slides 型アーティファクトとする。
Google スライドが必要なときは、アーティファクトの書き出し機能で変換する。
PPTX ファイルが必要なときだけ python-pptx で作る。

### Slides アーティファクトの手順

型の作成結果が返す指示が正本で、ここはその要約とする。
食い違えば作成結果に従う。

1. `Artifact` の `quickstart` を `intent: "slides"` で呼び、Slides 型の `type_url` と標準のデザインシステムを受け取る
2. `type_url` と `title` と `auto_open: "after_first_write"` で新規作成する。作成結果に型の指示と、先に読むページ `deck-files.md`、`format.md`、`fonts.md` が入るので、全部読む
3. デザインシステムの `project/README.md` と `project/colors_and_type.css` を読み、トークンを取る。`project/api/tokens.md` と `project/tokens.json` は無いので読まない
4. 元ファイルを `drafts/deck-<slug>/` に置く。`project/deck.json` と `project/slides/<id>.html` の構成にする
5. 最初の公開は `deck.json` と表紙の枚だけを1回の publish で送る。`url` に作成結果の URL、`root` に `drafts/deck-<slug>` の絶対パス、`file_path` に deck.json の絶対パス、`files` に root 相対の辞書で表紙を渡す
6. 以降は数枚ずつ、送るファイルだけを `files` に入れて公開する。`index.html` と `artifact-type/` は送らない
7. 各枚の `<aside>` に話し手メモを書く。Google スライドへ書き出すとスピーカーノートになる
8. `drafts/deck-<slug>/README.md` に、公開URL、作成日、直し方、枚の一覧、数字の出どころ、確認事項を書く

型の指示は、検証のための読み返しと画面確認を禁じている。
初稿の見た目の確認は人が行う前提にし、受け渡しのときにそう伝える。

公開のあとにページ側で編集されることがある。
再公開の前に `action: "read"` で公開版を取り直し、差分を取り込んでから出す。

### deck.json の雛形

```json
{
  "v": 4,
  "createdOnFiles": {"v": 1, "at": "<ISO 8601 の日時>"},
  "lists": "css",
  "title": "<資料名>",
  "cover": "cover",
  "order": ["cover", "ask", "agenda", "..."],
  "sections": {
    "s0": {"description": "本日の判断と全体像", "start": "cover"},
    "s1": {"description": "<章名>", "start": "<その章の最初の id>"}
  },
  "faces": {
    "ibm-plex-sans-jp": {"family": "IBM Plex Sans JP", "href": "https://fonts.googleapis.com/css2?family=IBM+Plex+Sans+JP:wght@400;700&display=swap"},
    "ibm-plex-sans": {"family": "IBM Plex Sans", "href": "https://fonts.googleapis.com/css2?family=IBM+Plex+Sans:wght@400;700&display=swap"},
    "ibm-plex-mono": {"family": "IBM Plex Mono", "href": "https://fonts.googleapis.com/css2?family=IBM+Plex+Mono:wght@400;700&display=swap"}
  },
  "designSystems": [
    {
      "title": "AtomicSoftware Slide Design System",
      "namespace": "atomicsoftware",
      "artifact": "https://claude.ai/artifact/8i2kJMwzZosAxYG1YakaVc",
      "version": "<作成結果に書かれた版>",
      "copiedAt": "<ISO 8601 の日時>"
    }
  ]
}
```

`faces` は書体ごとに Google Fonts の css2 リンクを書く。`colors_and_type.css` の `@import` は使えない。
`designSystems` の記録は必須だが、このデザインシステムは `tokens.json` を持たないため、ロゴ画像だけを `project/ds/atomicsoftware/assets/` にサーバ側コピーする。

### 枚のHTMLの規則

- 1枚は `<section id="<id>">` 1つ。`data-transition="fade"` を付ける
- スタイルはすべてインラインで書く。`class`、`var()`、`margin`、`em` は使えない。`padding` と `gap` で間隔を作る
- 配置は `display:flex` と `grid` のフロー配置を標準にする。`position:absolute` は持ち帰りの1行とフッターにだけ使う
- 文字サイズは 24px 以上
- 色と書体はトークンの値をそのまま書く。パレット外の色を使わない
- `<aside>` は section の最後の子に置く
- 画像は `assets` に上げ、返ってきた URL をそのまま参照する

本文の枚の雛形。

```html
<section id="<id>" data-transition="fade" style="background:#F4F4F4;color:#202222;font-family:'IBM Plex Sans','IBM Plex Sans JP',Arial,sans-serif;padding:128px 128px 240px;display:flex;flex-direction:column;gap:48px">
<div style="display:flex;flex-direction:column;gap:12px">
<p style="font-size:24px;color:#616565;letter-spacing:2px"><章番号> <章名></p>
<h2 style="font-size:52px;font-weight:700;line-height:1.25;letter-spacing:2px"><結論を書いた見出し></h2>
</div>
<div style="display:flex;gap:32px">
<div style="flex:1;display:flex;flex-direction:column;gap:16px;background:#FFFFFF;padding:40px;border:1px solid #BBBDBD">
<p style="font-size:24px;color:#616565"><カードの小見出し></p>
<p style="font-size:28px;line-height:1.5"><カードの本文></p>
</div>
</div>
<p style="position:absolute;left:128px;bottom:176px;width:1664px;font-size:28px;font-weight:700;line-height:1.4"><持ち帰りの1行></p>
<div style="position:absolute;left:128px;right:128px;bottom:64px;display:flex;justify-content:space-between">
<p style="font-size:24px;color:#616565"><出典と注記></p>
<p style="font-family:'IBM Plex Mono',Courier New,monospace;font-size:24px;color:#616565"><n> / <全体></p>
</div>

```

推奨案のカードは `border:4px solid #FF4600` にする。
目次の再掲の枚は、今の章を #202222 の太字、他を #9EA2A2 にし、本文と持ち帰りの1行を置かない。

### README の雛形

`drafts/deck-<slug>/README.md` には次の見出しを立てる。

1. 公開先。公開URL、作成日、枚数、デザインシステム、位置づけ、読む相手、求める判断
2. 直し方。枚の HTML の場所、順序の変え方、`url` と `root` と `file_path` を渡して再公開する手順、`action: "read"` で取り直す注意
3. 枚の一覧。番号、id、役割、見出し
4. 数字の出どころ。数字、出典、地位
5. 確認事項。聞くはずだった質問と置いた仮の答え、言い換えた語と元の語
6. 起案後に追記すること。相手の反応、通ったか、次回変えること

### PPTX で作るときの制約

この環境では node と LibreOffice が動かない。
python-pptx を venv に入れて使い、目視の代わりに座標検算で確かめる。

1. `python3 -m venv venv && ./venv/bin/pip install -q python-pptx lxml defusedxml`
2. スライドは 13.333in × 7.5in。左右の余白 0.62in のとき使える幅は 12.09in
3. 横並びのカードは、3枚なら幅 3.84in と間隔 0.28in、5枚なら幅 2.0in と間隔 0.36in
4. 全図形の座標を読み、下端 7.0in 超過、右端 12.85in 超過、矩形の重なりを機械的に検算する
5. `srgbClr` の値を全部拾い、パレット外の色がゼロかを数える
6. 成果物は `SendUserFile` で渡す。Google スライドが必要なら Drive に入れると自動変換される

## Step 7: 点検する

提出前に次を順に確かめる。1つでも落ちていれば直してから出す。

### 判断の点検

- 何を決めるのかが2枚目で分かるか
- 推奨は何か、なぜ代替案より望ましいのか
- どの主張が事実で、どれが観察か仮説か未確認か
- 承認後に何が起き、誰が担当するか
- 成功と失敗をどう測るか
- どんな根拠が出たら方針を変えるか

### 見せ方の点検

- 冒頭の2枚で、聞いたあとの状態と全体像を出したか
- 判断を求める章の前に現在地を示しているか
- 答えを後回しにする箇所で「あとで説明する」と約束し、回収したか
- 1枚1メッセージになっているか
- 各枚に持ち帰りの1行があるか
- 見出しだけを順に読んで主張が伝わるか
- レイアウトの型を構造から決め、種類を絞ったか
- 色は3色までか。Orange は1枚に1つの役割か。太字は役割の外で使っていないか
- 文字と背景のコントラスト比は 4.5:1 以上か。色だけで意味を伝えていないか
- 棒グラフの基準値は 0 か。比較の基準を示したか。項目の並びに意味があるか
- 図表の単位、出典、時点、定義を添えたか
- 余白が 20〜30% 残っているか。カードの幅、間隔、上端がそろっているか
- 締めは行動の依頼になっているか
- 検討の経緯、AIとのやりとり、捨てた案、相手がすでに知っている背景が残っていないか

### 表記の点検

regulation-notation の禁止表現と固有名詞ルールに照らす。
japanese-tech-writing の「LLMっぽい表現の禁止」と「冗長の排除」、natural-japanese の語彙表で推敲する。

機械的な検査を先に回す。
話し手メモは本文と別に数えるため、`<aside>` を除いた版を先に作る。

```bash
D=drafts/deck-<slug>/project/slides
T=$TMPDIR/slides-body
mkdir -p "$T"
for f in "$D"/*.html; do
  perl -CSD -0777 -pe 's/<aside>.*?<\/aside>//gs' "$f" > "$T/$(basename "$f")"
done

# 禁止語。本文と話し手メモの両方を対象にする
for w in "・" "——" "ーー" "＝" "！" "画期的" "革新的" "唯一無二" "一切" "完全に" "非常に" "極めて" "させていただ" "まず" "重要なのは" "と言えるでしょう" "多角的" "にあたる" "という形" "入口" "土台" "本質" "核心" "ブレーキ" "障壁" "解像度" "手触り" "肌感" "刺さる" "効いて" "回って" "回す" "化ける" "走らせ" "基本的に" "おおむね" "かなり" "Medicalforce" "MedicalForce" "medical force" "メディカルフォース"; do
  n=$(grep -o "$w" "$D"/*.html | wc -l | tr -d ' ')
  [ "$n" != "0" ] && printf "%-12s %s\n" "$w" "$n"
done

# 括弧補足。曜日だけ許す
grep -n "（" "$D"/*.html | grep -v "（[月火水木金土日]）"

# 絵文字
perl -CSD -ne 'print "$ARGV:$.: $_" if /[\x{1F300}-\x{1FAFF}\x{2600}-\x{27BF}]/' "$D"/*.html

# 色の一覧と、枚ごとの Orange の数
grep -oE "#[0-9A-Fa-f]{6}" "$D"/*.html | sort | uniq -c | sort -rn
grep -c "#FF4600" "$D"/*.html

# 文字量。見出しの字数と、見出しと持ち帰りと注記を除いた本文の字数
for f in "$T"/*.html; do
  perl -CSD -0777 -ne '
    my $h = /<h2[^>]*>(.*?)<\/h2>/s ? $1 : "";
    $h =~ s/<[^>]+>//g; $h =~ s/\s//g;
    s/<h2.*?<\/h2>//s;
    s/<p style="position:absolute[^"]*bottom:176px[^>]*>.*?<\/p>//s;
    s/<div style="position:absolute[^"]*bottom:64px.*?<\/div>\s*<\/div>//s;
    s/<[^>]+>//g; s/[\s\p{P}\p{S}]//g;
    printf "%-16s h %2d  body %3d\n", $ARGV, length $h, length $_;
  ' "$f"
done
```

`grep -P` は macOS の BSD grep では動かないので、Unicode の範囲は perl で検査する。
引っかかった語は1つずつ文脈を見て判断する。
「まず」は時系列の始まりなら残す。「回す」は「次回に回す」のような順序の意味なら残す。
色の一覧にパレット外の値があれば置き換える。
Orange が1枚に2つ以上あるときは、同じ役割かを確かめる。
見出しが 32 文字を超える枚と、本文が 200 文字を超える表以外の枚は、Step 3 の目安に戻して削る。
perl の出力の `h` は見出し、`body` は本文の字数で、ラベルを ASCII にしているのは `-CSD` がスクリプト内の日本語を文字化けさせるため。

話し手メモも声に出す想定で読み、息が切れる文と、言いよどむ箇所を直す。
違和感が消えるまで繰り返す。
